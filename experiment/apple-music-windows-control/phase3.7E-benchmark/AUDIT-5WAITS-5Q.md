## 1. 五问矩阵

| # | 位置 / 时长 | ①在等什么状态 | ②状态由谁产生 | ③后面是否有 condition-poll | ④是否成功路径 | ⑤可否替代为状态条件 | 失败模式（若删掉） |
|---|---|---|---|---|---|---|---|
| W1 | `:412` **120 ms** | 光标已落在列表区域的滚动点上、应用完成 hit-test，随后的滚轮事件才作用在列表而不是别的控件上 | OS 输入栈 + WinUI hit-testing（应用侧） | 否（紧跟的是滚轮注入；其后的 poll 等的是"滚动结果"，不是"光标就绪"） | 是（只要走滚动路径就先执行） | **依据弱**：没有可观测的"hover 已生效"状态；唯一代理是 `AutomationElement.FromPoint`，而该链路已记录 UIA pattern 调用有副作用（会 re-empty 矩形） | 滚轮落到错误位置 → 滚动无效 → `OUT_OF_VIEW` / `TARGET_ROW_NOT_FOUND`（良性失败码） |
| W2 | `:415` **450 ms** | 滚轮注入后，结果列表的滚动动画 + WinUI 虚拟化/realize 完成，产生新的行几何 | 应用滚动动画与虚拟化 | **是**：`Scroll-AmView` 返回后立即 `:477` 250 ms → `:478 Wait-AmRect`（100 ms 轮询 / 600 ms 预算），等的正是"行有非空矩形" | **否（恢复路径）**：仅当行在视口外或可见比 < 0.7 时才会走到滚动分支 | **有确切答案**（§7.1 第 3 问 = 是）→ 预测明确：该 450 ms 大概率被后续 poll 部分/完全吸收 | 读到过期几何 → `OUT_OF_VIEW`；或对已不在该位置的行发起点击 → `SMTC_WRONG_TRACK`（由 L3 校验层裁决，不会静默误放） |
| W3 | `:517` **350 ms** | `SetForegroundWindow` 之后：目标窗口**真的**成为前台，并完成随之而来的移动/重排，使随后重读的 `BoundingRectangle` 与点击瞬间一致 | OS 前台切换 + WinUI 布局 | **否**：`:524` 只读一次矩形，只有 `Test-AmRectSane`，**没有任何等待/重试/校验** | **是（每一次点击）**：`Invoke-AmRowPlay` 在非 `-NoForeground` 时总执行 | **可以**：状态"本窗口是前台"直接可观测（`GetForegroundWindow() == $Hwnd`），本仓库的 `phase3.7E-benchmark/lib/bench-common.ps1` / 3.7B `AmNav.Native` 已有该调用 | **高代价**：窗口尚未前台时点击会**注入到别的窗口**（benchmark 期间前台是操作者的 msedge）——这是对无关应用的真实副作用，不是良性失败码 |
| W4 | `:533` **200 ms** | `SetCursorPos` 之后、双击之前：光标位置生效且应用完成对新位置的 hit-test | OS 输入栈 + 应用 hit-testing | 否（其后直接注入 down/up） | 是（每次点击） | **依据弱**：同 W1，"hit-test 就绪"无廉价可观测状态 | 双击落在旧位置/错误行 → `SMTC_WRONG_TRACK` 或 `CLICK_FAILED` |
| W5 | `:535` **130 ms** | **不是"等状态"**：它是双击两次 down/up 之间的**输入整形间隔**，让两次点击被识别为 double-click | OS 双击判定 + 应用 | 否 | 是（每次点击） | **不适用**：它不是在等某个状态，而是在构造输入时序 | 两次点击被判成两次单击 → 播放/暂停互相抵消（净无效），或只选中不播放 → `SMTC_TIMEOUT` |

**结论（第 2 步产出）**：五个 wait 分成三类——**吸收候选**（W2：后面紧跟 condition-poll）、**同步关键/需要状态替换**（W3：无 poll 兜底，但状态可观测）、**输入时序整形**（W5：不是状态等待，不适用"删除"这一手术）。W1/W4 属于"注入前置等待"，其状态无廉价观测手段，理论依据最弱。

## 2. 候选选择（第 3 步）

**本轮选定：W2（`am-uia.ps1:415`，450 ms）**，理由按 §7 判据而非毫秒数：

1. §7.1 第 1 问有确切答案：它在等"滚动/虚拟化产生新行几何"。
2. §7.1 第 3 问有确切且**可伪证**的答案：后面确实紧跟 `Wait-AmRect` 条件轮询 → 预测是"该 450 ms 被部分或完全吸收"，
   与 ⑤ 的 500 ms 同类但**更干净**（⑤ 的 500 ms 在导航函数里，吸收它的 poll 隔了一层；W2 的 poll 就在 3 行之后）。
3. 失败模式有界且被 L3 覆盖：最坏是 `OUT_OF_VIEW` / `TARGET_ROW_NOT_FOUND` / 被 SMTC 判定的 `SMTC_WRONG_TRACK`，
   **不会向无关应用注入输入**。
4. W2 属于**恢复路径**（不是每次都会走），因此即便有收益，其量级也只体现在走该路径的曲目上——这一点在解释结果时
   必须声明，不得把"聚合差值≈0"直接说成"已被吸收"。

**W3 暂缓（不因毫秒更大而优先）**：它其实是"每次点击都付 350 ms"、且**没有任何 poll 兜底**，从 ④ 延迟量级看最值得研究；
但把它按 ⑤ 同构方式"450→0 式删除"会引入**对无关窗口的点击注入风险**，而它正确的改法是**把固定等待替换为可观测状态条件**
（轮询 `GetForegroundWindow() == $Hwnd`，上限 350 ms，超时即不点击/按失败处理），这属于"改一个 wait 的实现方式"而不是"删一个数字"。
本审计只做只读判断，是否采用该改法、以及要不要在操作者的桌面上承担该实验，留待操作者决定。

**W1 / W4 不选**：第 5 问（可替代为状态条件）无干净答案，理论依据最弱。
**W5 不选**：它不是状态等待，删除它等价于改双击输入时序，风险错位（可能变成"两次单击"）。

## 3. 受控实验设计（第 4 步，与 ⑤ 完全同构）

- **改动**：`poc/lib/am-uia.ps1:415` `Start-Sleep -Milliseconds 450` → `0`。**只此一行**，其余（含 `:477` 的 250 ms）不动。
- **夹具**：`phase3.7E-benchmark/cases/songs-20-pinned.json`，同 20 首、同序、每首一次、`Retries 0`、resolver 在测量窗口外。
- **外部观测协议**：与 ④/⑤ 相同——`run-bench.ps1 -All -NoWait`，gate ii（目标非正在播放）、非最小化、非前台、当前桌面；
  每轮结束恢复前台与光标。
- **对比基线**：④ `reports/bench-20260926-090320.jsonl`（原版代码）；同时与 ⑤ `bench-20260926-090905.jsonl` 做交叉看。
- **观测分辨率（必须声明）**：请求 50 ms 轮询 → 实测 median 80 / mean 82 / max 121 ms；低于该分辨率的差值不报为收益；
  单次最小值只是下界；`T7` 不可观测，禁止编造。
- **记录**：correctness、**失败集合单独记录**、每个 stage、`t.*`、`contentMatchMs`、occupancy（`T10 − T3`）。
- **预测（可伪证）**：
  - 若 450 ms 被 poll 吸收 → 配对 occupancy 差值应**明显小于 −450 ms**（含 ≈0）+ 失败集合不变；
  - 若它是同步关键 → 失败集合出现 `OUT_OF_VIEW` / `TARGET_ROW_NOT_FOUND` / `SMTC_WRONG_TRACK`，或 `stageDetail` 出现滚动相关恶化。
- **处置（三分支，第 5 步）**：稳定可归因收益 → 保留；无可归因收益 → 回退；correctness/时序受影响 → 回退并记录原因。

## 4. 审计本身的局限（必须与结论同时引用）

- 本审计是**静态阅读**，不是运行测量；"状态由谁产生"是基于代码与既往阶段实测（3.7A/3.7B/3.7D）的推断，
  已在表中标明哪些是代码事实、哪些是推断。
- benchmark 行**不记录 `Scroll-AmView` 的调用次数或 `scrollSteps`**，因此 W2 的**暴露度未知**：只有行在视口外
  （或可见比 < 0.7）时才走该路径。解释 W2 实验的"≈0 差值"时，必须区分"被 poll 吸收"与"该曲根本没走到这条路"，
  在无法区分时**只能报告为不可区分**，不得择一断言。
